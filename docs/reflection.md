# Project Reflection

This project gave me practical experience in building an end-to-end machine learning system rather than treating model development as an isolated activity. I began by implementing a PyTorch convolutional neural network for Fashion-MNIST, together with reusable dataset utilities and a YAML-driven training program. The configuration file made important parameters such as epochs, batch size, learning rate, early-stopping patience, data location, and checkpoint name explicit and version controlled. Structured JSON-line metrics also made the training output easier to inspect and potentially integrate with monitoring systems.

The next stage was converting the trained model into a usable service. I implemented a FastAPI application with separate health and prediction endpoints. The prediction endpoint validates an uploaded image, applies the same preprocessing used during training, and returns both the selected class and probabilities for all ten Fashion-MNIST categories. Testing the API helped demonstrate that successful model training alone is insufficient; preprocessing, checkpoint loading, error handling, and response design are equally important in a deployable ML system.

Containerization highlighted the importance of reproducible environments. I created separate images for training and serving so that each workload had a clear responsibility. The serving container uses a slim Python image, runs as a non-root user, exposes only the required port, and includes a health check. During validation, I found accidental command text appended to `dataset.py`, which caused a container-time syntax error. Diagnosing the traceback, correcting the source file, rebuilding the image, and repeating the test reinforced the value of automated syntax checks and clean commits.

Kubernetes was the most instructive part of the work. The training Job used a ConfigMap, resource requests and limits, temporary dataset storage, and a persistent volume for the checkpoint. The serving Deployment then consumed the same persistent checkpoint through a Service with readiness and liveness probes. The HorizontalPodAutoscaler demonstrated how resource requests and metrics support scaling decisions. I also learned that Docker Desktop and Minikube maintain separate image stores, so locally built images must be loaded into Minikube before deployment.

Finally, the feature-branch and pull-request workflow created a clear and auditable development history. GitHub Actions now checks unit tests, Python syntax, YAML files, and Dockerfiles automatically. Overall, the project connected model development, API design, containers, orchestration, testing, and version-control practices into one reproducible MLOps workflow.
